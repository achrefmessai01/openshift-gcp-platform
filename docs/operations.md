## 1. Access

| What                    | How                                                                     |
|-------------------------|-------------------------------------------------------------------------|
| OpenShift console       | `https://console-openshift-console.apps.<cluster>.<base-domain>`        |
| CLI                     | `oc login https://api.<cluster>.<base-domain>:6443 -u <user>` (htpasswd IdP, group `platform-admins`) |
| Pipeline identities     | Per-namespace service accounts with `edit`; tokens stored as masked CI variables |
| Nodes                   | `gcloud compute ssh core@<node> --tunnel-through-iap` (break-glass only; prefer `oc debug node/<node>`) |
| Bastion (optional)      | `gcloud compute ssh ocp-bastion --tunnel-through-iap`                   |
| Kibana                  | `https://kibana-elastic-system.apps.<cluster>.<base-domain>`, user `elastic` (secret `logging-es-elastic-user`) |
| Grafana / metrics       | Console → Observe (platform and user-workload metrics, alerts)          |

## 2. Daily checks (5 minutes)

```bash
oc get clusterversion                       # Available=True, Progressing=False
oc get clusteroperators | grep -v 'True.*False.*False'   # should print only the header
oc get nodes                                # all Ready
oc get pods -A | grep -Ev 'Running|Completed'            # should be empty
oc -n subscriber-api-prod get deploy,hpa,pdb,route
oc -n openshift-monitoring get alertmanager main -o jsonpath='{.status}' ; echo
tools/netcheck.sh api.<cluster>.<base-domain> subscriber-api.apps.<cluster>.<base-domain>
```

Alerts are routed from Alertmanager to the platform webhook (chat/ticketing); `Watchdog` is
silenced on purpose and must keep firing (dead-man switch).

## 3. Deployment procedure

Standard deployment is done by the pipeline (`deploy:<env>` jobs). Manual equivalent:

```bash
export API_KEY=...                                   # value of the application secret
scripts/deploy.sh staging v0.1.0 --acceptance        # apply overlay, set image, wait, run acceptance
```

Checklist before a production deployment:

1. Staging acceptance record is `ACCEPTED` and the JMeter gate is `ACCEPTED`.
2. Change ticket approved, maintenance window if the change touches the platform.
3. `oc -n subscriber-api-prod rollout history deployment/subscriber-api` noted (rollback target).
4. Deploy, then run the production smoke tests (`--include smoke --include platform`).

## 4. Rollback procedure

```bash
scripts/rollback.sh prod            # previous revision
scripts/rollback.sh prod 7          # a specific revision from the history
```

The script performs `oc rollout undo`, waits for the rollout and re-runs the smoke suite so
the rollback is verified, not assumed. Infrastructure rollback = revert the merge request
and let the pipeline plan/apply again; never edit cloud resources by hand.

## 5. Scaling

| Need                     | Action                                                             |
|--------------------------|--------------------------------------------------------------------|
| More application capacity| HPA handles 2→6 (prod 3→10) replicas on CPU; raise `maxReplicas` in the overlay |
| More cluster capacity    | `oc scale machineset <name> -n openshift-machine-api --replicas=N` |
| Bigger nodes             | New MachineSet with the new machine type, drain and delete the old one |
| NAT port exhaustion      | Increase `min_ports_per_vm` in `terraform/modules/network` (Cloud NAT logs show `allocation_status`) |

## 6. Certificates

- `*.apps` and API certificates are generated by the installer (internal CA) and rotated
  automatically. For a public CA, add a custom ingress certificate
  (`oc -n openshift-ingress create secret tls ...` then patch `ingresscontroller/default`).
- `RP-003` in the platform suite fails when a Route certificate expires in less than 14 days;
  `tools/netcheck.sh` prints the expiry date.

## 7. Backups

| Asset                      | Mechanism                                                      | Frequency |
|----------------------------|----------------------------------------------------------------|-----------|
| etcd                       | `oc debug node/<master> -- chroot /host /usr/local/bin/cluster-backup.sh /home/core/backup` then copy to GCS | daily (cron job on bastion / pipeline schedule) |
| Image registry             | GCS bucket versioning (3 noncurrent versions kept)             | continuous |
| Terraform state            | GCS bucket versioning                                          | continuous |
| Platform configuration     | Git (Terraform, Ansible, manifests): the cluster is re-creatable | per commit |
| Application data           | None: subscriber-api is stateless by design                    | n/a |

Restore of etcd follows the OpenShift "restoring to a previous cluster state" procedure;
rehearse it on a non-production cluster before relying on it.

## 8. Upgrades

1. Read the release notes and check `oc adm upgrade` for the recommended target.
2. Make sure `PodDisruptionBudget`s allow node drains (prod keeps 2 replicas available).
3. `oc adm upgrade --to=<version>` during a maintenance window; follow
   `oc get clusterversion -w`.
4. After the upgrade: daily checks (section 2), production smoke tests, ECK operator and
   Elasticsearch health.

## 9. Monitoring and alert catalogue

Rules live in `deploy/base/prometheusrule.yaml` and are evaluated by user-workload monitoring.

### SubscriberApiDown
- **Severity**: critical. No pod scraped for 5 minutes.
- **Check**: `oc -n <ns> get pods`, `oc -n <ns> describe deploy subscriber-api`, events.
- **Likely causes**: image pull failure (registry credentials, tag), failing startup probe,
  quota exhausted, NetworkPolicy blocking the monitoring namespace.
- **Action**: fix the cause or roll back (section 4).

### SubscriberApiHighErrorRate
- **Severity**: warning. More than 5 % of requests end in 5xx for 10 minutes.
- **Check**: `oc -n <ns> logs deploy/subscriber-api --since=15m | grep '"level":"ERROR"'`,
  Kibana filter `kubernetes.deployment.name: subscriber-api`.
- **Action**: identify the failing route from `http_requests_total`, roll back if introduced by
  the last release, otherwise open an L3 ticket with the request samples.

### SubscriberApiHighLatency
- **Severity**: warning. p95 above 500 ms for 10 minutes.
- **Check**: CPU throttling (`container_cpu_cfs_throttled_seconds_total`), HPA at max,
  node pressure (`oc adm top nodes`).
- **Action**: scale (section 5), review resource requests, compare with the last JMeter report.

### SubscriberApiPodRestarting
- **Severity**: warning. More than 3 restarts in 30 minutes.
- **Check**: `oc -n <ns> logs --previous`, OOMKilled in `oc describe pod`.
- **Action**: raise memory limit in the overlay or fix the leak; keep the incident record.

## 10. Troubleshooting playbook

| Symptom                                   | First checks                                                                 | Usual fix |
|-------------------------------------------|------------------------------------------------------------------------------|-----------|
| Route returns 503                         | `oc get endpoints subscriber-api`, readiness probe, NetworkPolicy `allow-from-openshift-ingress` | fix readiness / policy |
| `ImagePullBackOff`                        | tag exists? pull secret linked to the ServiceAccount? registry reachable through NAT (FW-009)? | correct tag / secret |
| Pod `CrashLoopBackOff`                    | `oc logs --previous`, `API_KEY` secret present, read-only FS writes (`/tmp` only) | fix config |
| `oc login` times out                      | Your IP in `admin_cidrs`? `tools/netcheck.sh` TCP 6443, API load balancer health | update flow matrix FW-001 |
| Nodes `NotReady` after scale-up           | Cloud NAT logs (image pull failures), machine-api events                      | NAT ports / quotas |
| New project cannot reach another project  | Default-deny NetworkPolicies from the project template                        | add an explicit policy |
| Elasticsearch yellow/red                  | PVC bound? memory limit vs heap? `oc -n elastic-system get es,kb,beat`        | resize / add node |
| Terraform plan shows unexpected changes   | Drift: someone edited the console; compare with `plan.txt` artifact          | re-apply from Git |

Network diagnostics: `tools/netcheck.sh <api-host> <route-host>` (DNS, TCP, TLS expiry, HTTP
expectations, path, cluster operators). Packet captures on a node:
`oc debug node/<node> -- chroot /host tcpdump -i br-ex port 443 -w /host/tmp/cap.pcap`.

## 11. Support model

| Level | Who                 | Scope                                               | Target      |
|-------|---------------------|-----------------------------------------------------|-------------|
| L1    | Service desk        | Ticket intake, known-error database, user access    | 15 min ack  |
| L2    | Operations          | Daily checks, deployments, rollbacks, scaling, alert handling | 1 h ack, 4 h restore (P2) |
| L3    | Integration team    | Root cause analysis, platform changes (flow matrix, Terraform, Ansible), vendor escalation (Red Hat, Google) | 4 h ack, workaround ≤ 1 business day |

Ticket workflow: open → qualified (P1–P4) → in progress → resolved → closed after user
confirmation. P1 (production down) triggers the on-call bridge and a post-incident report
within 5 business days using [incident-report-template.md](incident-report-template.md).
A monthly incident report consolidates tickets, MTTA/MTTR and recurring problems.

## 12. Maintenance windows and change control

- Standard window: Tuesday and Thursday 20:00–23:00 (cluster local time); emergency changes
  need an L3 lead approval.
- Every change is a merge request: review by a second engineer, pipeline green, flow matrix
  updated when a port opens, acceptance record attached to the ticket.
